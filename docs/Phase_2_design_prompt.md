# Design prompt — Phase 2 "Sandbox Stages" surfaces (for Claude Design)

**What this is:** the interaction-design brief for every new Phase 2 screen in
cradle. Deliverable format follows the two precedents that worked —
`cradle/design_handoff_agent_panel/` and `cradle/design_handoff_dialogue/`:
a **README** (full interaction spec: state tables, exact copy, keyboard, empty/
error states), a **PLAN** (implementation map: component tree, store slices,
build order), and **artboards in both themes**. Design all screens before any
build; the PRD finalizes against this package.

**The package explores PROCESSES as well as editing surfaces.** For every
flow in §8a, board the journey end to end (what the user sees at each step,
where approval/spend/QA happens), not just the screens it passes through.
Where a process is undecided, produce comparison boards so the decision can
be made by looking.

---

## 1. Context — the product and its design system

Cradle is a Tauri 2 / React 19 desktop editor over game packs generated by the
`canon` CLI — "Cursor for game dev." Phase 2 turns it into a set of live
tuning sandboxes: the game is the primary lens; pack data stays the source of
truth; every write goes through a canon verb.

**Locked visual system (do not reinvent):**
- Aesthetic per `cradle/design_handoff_editor_worldmap_start/PLAN.md`: clean
  dev-tool (Linear / Raycast / Arc family), warm-neutral base, dark + light
  designed together (dark-first), Inter + JetBrains Mono, neutrals + one
  accent + semantic colors only. All chrome colors from `src/styles/tokens.css`.
- Shell: 36px TopBar / 208px LeftNav / center DetailPane / 24px ValidationBar.
- The **agent panel** (Phase 1, `design_handoff_agent_panel/`) occupies a right
  column — default 412px, min 340, max 720, collapsible to a 40px rail. Every
  Phase 2 screen must work with it expanded (canvas absorbs width loss;
  floating panels reflow inward below 900px of remaining main width).
- House doctrine, enforced in the existing UI: **disabled-with-a-reason beats
  hidden** (greyed controls carry the reason on the tooltip); **paid actions
  read as paid before any confirm** (estimate on the button, e.g.
  `Generate · $0.07–$0.30`); validation chips are cleared by any edit so a
  stale "valid ✓" never describes an edited level.
- Existing surfaces to EXTEND, never replace: level editor (`LevelDetail` +
  bottom Dock palette + left ToolRail + pan/zoom canvas + minimap), the
  Animation tab (state selector, filmstrip scrubber, offset nudge pad, timing
  edits), AnimateModal, the History/lineage tab, CommandPalette.

## 2. Screen A — Character mode: the feel-tuning panel

The spine of Phase 2. The user plays a level, feels something off, opens
character mode, and tunes physics against the real level in a live session.

**Data it edits (all real, spec-driven — sliders generate from the schema):**
- Movement (pack-wide, per-level override): `run_speed, walk_speed,
  jump_height, jump_width, gravity, ground_accel, ground_friction,
  brake_accel, air_accel, air_friction, run_up_cells, coyote_s`.
- Combat: `player_max_hearts, stomp_damage, stomp_bounce_factor,
  hurt_iframes_s, spawn_grace_s`. Rules: `platform_drop_through,
  chase_speed_mult, break_delay_s, death_linger_s`.
- Every knob has a **band** (min/max, e.g. gravity 15–60). Bands are
  pack-registry data and **user-widenable** — design the affordance for
  "widen this band" (it is a journaled schema edit, not a casual drag).

**Required interactions & states:**
1. **Scope toggle** per knob group: "this level" (override) vs "whole game"
   (pack-wide). Show clearly when a level override shadows the pack value,
   with a one-click "clear override."
2. **Live session strip**: which engine is running (pygame/godot chip), which
   level, session state (`live` = channel connected / `stale` = edits not yet
   in session / `relaunching` / `not running`), and controls: ▶ launch in
   sandbox, ⟳ restart, ⏹ stop. Latency contract (three separate promises —
   design the feedback for each): generation legs are API-bound and take what
   they take (honest progress, never a fake spinner); the local loop is ours
   (constant swaps ≤250 ms, relaunch ≤3 s, local rebuild ≤1 s); and once
   generated bytes are on disk they are viewable/usable in the front end in
   ≤100 ms.
3. **Spawn-point picker**: choose where the player spawns for this session
   (click the minimap/canvas) so tuning happens at the problem spot.
4. **Advisory demotion**: on a code-evolved project, some keys are
   `code-owned` (the engine copy no longer reads the manifest value). Those
   sliders demote to a visibly-inert advisory state with the reason and a
   deep-link: "open in agent" (routes to the game_coder). Never hide them.
5. **Derived values**: jump velocity is computed (`√(2·g·(jump_height+0.4))`)
   — show derived readouts (jump apex time, max jump distance at run speed)
   so the numbers mean something physically.
6. **Validate feedback**: every applied change re-runs the free validator;
   surface verdict chips inline (the level editor's chip language).
7. **Save boundary**: dragging is pre-save UI state; **Apply** is the verb
   write (journaled, restorable); no silent writes. Design the dirty/apply/
   revert affordance.

**Concept board requested — "traversal modes."** We are undecided whether
locomotion contexts (ground / air / water / climb / glide) become a named
system. Show what the panel looks like if knobs are **grouped by traversal
context** (water shows the volume params trio: speed_factor, gravity,
impulse) vs a flat list. One artboard each; we'll decide from the boards.

## 3. Screen B — Build mode: zone painting

Zones are typed rectangles on the level grid (existing music sections are the
degenerate full-height case). V1 payload types: **physics** (gravity/speed
multipliers, water params), **music** (track per zone — exists today as 1-D
regions), **event** (trigger payload), **camera** (framing override — designed
now to prepare for 3D).

- A zone tool on the existing ToolRail; drag-a-rect creation on the canvas;
  zones render as translucent typed overlays with name chips.
- Selecting a zone opens its payload editor in the Dock's tray pane (372px,
  the existing selection-inspector slot): type, name, the payload's fields
  (spec-driven like the tuning panel), z-order/priority when zones overlap.
- A zone list (per level) with visibility toggles; conflicts (two physics
  zones overlapping) surfaced as a warning, not blocked.
- Music regions' existing M-toggle merges into this system — migrate the
  mental model, don't strand it.

## 4. Screen C — the 2D pixel editor (sprites + tilesets)

The largest new surface. Mount: a **DetailPane tab** ("Pixels" — beside
Overview / Animation / History) on player, enemies, items, and tilesets.

**V1 tool set (locked):** brush, eraser, fill, color picker, rectangular +
freeform selection, transform, layers, alpha handling, palette constraint,
per-pixel work at sprite resolution, onion-skin + grid overlays. Explicitly
NOT v1: filters, effects, blend modes beyond normal, vector layers, brush
engine.

**What makes it ours (design these, they're the differentiators):**
1. **Palette constraint**: the pack's style palette (role → hex, from
   `style/<stage>/style.json`) is the default swatch set; painting off-palette
   is possible but visibly flagged (QA will meter drift). Show the palette
   rail with role names, not just hexes.
2. **Frame-aware editing**: for animated sprites, the editor opens on a
   frame within a state — reuse the Animation tab's state selector + filmstrip
   as the navigation (same components, same muscle memory). **Onion skin**
   shows prev/next frames from the real frame map at adjustable opacity.
3. **Tileset mode**: the tilesheet is a strip of slots with named tile types;
   editing is per-slot with slot boundaries locked (geometry is frozen —
   pixels repaint, regions don't move). Autotile-variant slots (16 variants
   of floor) show as a variant grid with "edit all variants' shared base"
   vs "edit this variant." **Joins are in scope**: blocks should join to
   break up repeating patterns (edge/corner join variants beyond floor) —
   design the join workflow: see the repetition, generate join variants
   (img2img, estimate-gated), hand-edit them here, approve.
3b. **Region recolor / reskin** (the skins system): select a region of any
   asset (sprite, portrait) and remap its colors — vary skin tone, change a
   cloak, produce a full reskin — creating variants or new characters from
   one asset. Pure code (no generation cost). Design its home: a tool in
   this editor, a quick-action on the entity, or both.
   Note: **no part layers** — 2D animation is frame-by-frame (rigging is
   3D-only, later); keep the layer model simple.
4. **Save = one version**: Save writes one provenance version (journaled,
   restorable via the History tab) and re-runs the free QA checks — surface
   **palette conformance** and **alpha gate** results as chips (warn, never
   block). Unsaved-work guard on navigation.
5. **Generate-then-tune flow**: entry points from generation results ("nudge
   two frames by hand" after picking a candidate) — design the handoff from
   AnimateModal's result into this editor.

Reference for behavior (never code): Aseprite/LibreSprite tool semantics and
keyboard defaults; Piskel's frame-first model; Pixelorama's timeline layout.

## 5. Screen D — Dialogue live-scene view (extension of the dialogue package)

`design_handoff_dialogue/` owns the graph editor + docked tester. Phase 2 adds
the **live half**: the same tester state drives a real running game session so
the branch plays in the world (NPC standing in the room, player walks up,
scene blocking visible, walk-away breaks reproducible).

- A "play this in game" affordance on the tester: launches/attaches a session
  (both engines eventually; design engine-agnostic), injects the simulated
  state, and boots to the NPC's room with the player nearby.
- The tester's state panel stays the authority; the live viewport is a
  window, not an editor. Show sync state (tester state ↔ session state) and
  a re-inject control after edits.
- Works for the dungeon crawler first; the platformer gains dialogue as a
  capability — design nothing platformer-specific.
- **Speaker portraits with moods are v1**: expressions are a closed enum
  (like animation states); the tester/scene shows the speaking character's
  emotion-sheet portrait per line. Design the portrait slot + the mood
  vocabulary's presence in the line editor.

## 6. Screen E — Play-session controls (small, global)

Phase 2 makes play sessions first-class: tracked, killable, live-linked.

- A session presence surface (status bar and/or TopBar chip): engine, level,
  live/stale, elapsed; click for a small popover with ⟳ restart / ⏹ stop /
  "make live" (connect channel).
- Multiple sessions are possible (e.g. one per engine): a compact registry
  list. The level editor's existing "playing… (Esc quits)" note upgrades
  into this system.
- Primary-engine concept: a project names a primary engine; the twin engine
  demotes visually wherever engines are picked (play buttons, session chips).

## 6b. Screen F — the asset Library (design now, build later)

Parked 2026-07 with the instruction "start from how reuse should FEEL" —
this package is that restart. The backend exists and is untouched
(`canon library publish/list/import`, a content-addressed global store,
cradle's 🗂 panel); nothing here builds until the design lands.

- **The publishable unit is a bundle, not a file**: a character = anchor
  (base/turnaround/optional 3D proxy ref) + animation states + expressions +
  skins; a tileset = sheet + slots + autotile + joins; audio = track + row
  metadata. Design browsing/preview around bundles.
- **Import adapts, not just copies**: the killer flow is importing an asset
  into a pack with a different palette — show a palette-adaptation preview
  (the recolor/conform machinery) before confirming. Import mints a fresh id
  and stamps lineage (`library_ref`) — surface that provenance.
- Publish flow (what's included in the bundle, name/tags), browse/search,
  and the relationship to the History/lineage view.
- Out of scope: engine copies/templates as library items; sharing beyond
  the local machine.

## 7. Constraints checklist for every screen

- Both themes, dark-first; tokens only; keyboard reachable; focus states.
- Coexists with the agent panel at 340–720px; degrades gracefully to 900px
  remaining main width.
- Disabled-with-a-reason for anything not yet wired.
- Paid actions carry the estimate on the button; free actions never confirm.
- Empty states, first-run states, and failure states specified in the README
  (the validator down, no session running, band widened beyond validator
  comfort, code-owned keys).
- Copy in the product voice: plain, specific, no apologies.

## 8a. Process explorations (flow boards, not screens)

Board each of these end to end — every step the user sees, where approval,
spend, and QA sit. These carry as much decision weight as the screens:

- **P1 — Character creation & consistency**: describe → anchor (three tiers:
  base image / turnaround sheet / optional 3D proxy — all v1 mechanisms;
  3D *editing* is v2 and only referenced) → approve & **lock** the anchor →
  batch-generate states + expression sheet conditioned on the lock → QA →
  hand-tune → reskin/recolor variants → the **re-anchor** flow (what
  invalidates, what survives).
- **P2 — Guided animation generation**: img2img with guidance — reuse the
  stored motion spec, upload your own example frames/references, per-state
  briefs; result → per-frame nudge handoff into the pixel editor.
- **P3 — Region recolor/reskin**: select → remap → save as skin or new
  variant; where the result lives (beside base, per the hash model).
- **P4 — Tileset joins**: spot repetition → generate join variants →
  hand-edit → approve → see the level canvas update.
- **P5 — The cascade moment**: an edit stales downstream artifacts; the
  plan-card flow (Phase 1's card language) with per-step confirm and the
  blast-radius cost rollup.
- **P6 — Expression sheets for dialogue**: mood enum → sheet generation →
  portraits appearing in the tester/live scene.
- **P7 — Library reuse**: publish a bundle from a project → browse from
  another → import with palette adaptation → provenance trail.

## 8. What to deliver

1. `README.md` — interaction spec: every state table, exact copy, keyboard
   map, the traversal-modes concept boards' verdict question stated.
2. `PLAN.md` — implementation map: component tree, store slices, which
   existing components are reused (Dock tray, ToolRail, Animation tab
   filmstrip, RowEditor spec-driven fields), and a numbered build order.
3. Artboards, both themes: Screen A (flat + traversal-grouped variants),
   B, C (sprite mode + tileset mode + joins), D, E, F — at 1440 logical
   width with the agent panel present in at least one board per screen.
4. Flow boards for P1–P7, each on one artboard where possible.
