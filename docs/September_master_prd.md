## 0. Problem & thesis

Three phase PRDs were authored in sequence, and later phases made decisions that re-shape earlier ones. Built in document order, September would produce: a registry frozen without the fields Phase 2 dispatches on, a journal schema changed three times, two price tables, two process-tracking paths, a second and third hardcoded label list, and a packaging pipeline made license-compliant only retroactively. This master is the reorder and re-inform that prevents that — one interleaved build plan, Phase 0 → 2, in which nothing is built that a later row undoes, works around, or impedes, and every screen that gets built has a named design source.

**The product thesis, stated once:**

- **The game is the primary lens.** The user plays, feels something wrong, and tunes against the real level in a live session. (UX thesis — Phase 2.)
- **Pack data remains the single source of truth, and every write is a canon verb.** Files are truth; engines are projections; the thesis never inverts the write path. (Architecture — all phases.)
- **Editing verbs live once in canon core; a game template is a declaration (`PackSpec`) the core dispatches on.** The dungeon crawler is the second registrant and the proving milestone; template #3 costs declarations, not another write layer. (Phase 0.)
- **Templates seed; projects own.** The template stamps a starting registry at create; from then on the pack's own data is the truth, and the intended lifecycle is divergence. This now extends to the agent layer (skills/recipes, §3.0-F) and to engine copies (every attached engine is a per-project, stamped, evolvable copy).
- **The agent is one loop with specialists as configuration.** Phase 1 builds the machinery once; Phase 2 adds configuration and tools (`mesh_smith` is config, not code), never a second orchestrator.

## 1. Doctrine — binds every row in §3

1. **Cradle never writes pack files.** Every mutation is a canon verb with `--actor`; the agent inherits this verbatim. The one write discipline: resolve → protected-field wall → fail-closed validate → warnings → `user_edited` stamp → journal per-field diff → CAS snapshot.
2. **Extend existing machinery, never parallel systems.** Each row names what it extends.
3. **Paid legs are user-run.** Estimates on the button as a range, from the single constants source (§3.0-C); paid reads as paid before any confirm; the agent may raise a paid suggestion card, never accept one. **Free never spend-confirms** — the $-tier cost dialog is reserved for real money; free and all-fake selections never see one, but ordinary ask-tier permission chips still apply (showing "$0").
4. **Disabled-with-a-reason beats hidden — for capability, not for mode.** Amended 2026-09-05 (hand-test pass, user-confirmed): the rule was being read as one case when it is two, and the conflation made surfaces confusing to work in.
   - **Capability-blocked** — the control belongs on this screen and in this mode, but something external stops it right now (no key set, no free endpoint, no project open, a grant not given). **Render it, greyed, and surface the reason.** Hiding it would hide both the explanation and the fix. The reason belongs in a tooltip on hover *or keyboard focus*, not as inline red text occupying the layout.
   - **Mode-inapplicable** — the control is not part of this mode's vocabulary at all (`+ new row` while in view or test mode). **Do not render it.** A permanently inert control is not information, it is noise.
   - The test: if answering *"why is this off?"* tells the user something they could act on, grey it and say so; if the honest answer is *"because you are not in that mode"*, it should not be on screen.
   - **Carve-out — a screen's primary action.** Where the blocked control *is* the action the screen exists for (the create wizard's Create button under a missing-key precheck), the reason stays **visible inline with its deep link**, not in a tooltip: a tooltip is too quiet for the one button that matters, and it cannot hold the link that fixes the problem. The tooltip rule governs secondary controls. Provisional (user-confirmed 2026-09-05, to revisit if it reads oddly in use).
5. **Honest progress, and the R2 latency contract** — three separate promises: generation legs are API-bound (elapsed + counts, never an ETA or a bar that lies; cancel keeps what landed and says what it cost — no latency promise); the local loop is ours (constant swaps into a live session ≤ 250 ms, relaunch ≤ 3 s, local rebuild ≤ 1 s); asset availability (bytes on disk are viewable in the front end in ≤ 100 ms — cache-busted reloads, never an app refresh).
6. **Nothing regenerates on its own; nothing is deleted.** NR (needs review) keeps working and keeps shipping; every write is a version; restore writes a new version.
7. **Platformer byte-identical throughout** the Phase 0 extractions — amended once at merge (Q6): the golden create fixtures gain an additive `bible.json` when `--orchestrate` becomes the create default; "byte-identical" reads "existing artifacts byte-identical; bible additive." The flip's only sanctioned fixture delta is `bible.json` — if the orchestrated create emits anything further, that is a new user decision, not a wider amendment (verify at P0-10).
8. **The I1–I8 invariants** (October's anti-lock-in set, as summarized in Phase 0's W4 stub) bind every new command in every phase: I1 all IPC through `invoke.ts` · I2 no new direct `@tauri-apps` imports · I3 new commands stateless (path + JSON) · I4 canon wheel-clean · I5 durable truth in `<pack>/.canon/`, never frontend-owned · I6 actor string centralized, every new verb takes `--actor` · I7 devMock parity for new commands · I8 localStorage = per-device convenience only. Plus the M0-readiness rule: backend/provider/template ids are data, never a hardcoded union.
9. **Design READMEs win on interaction and copy;** this master wins on scope, sequencing, and contracts. Prototype-only conventions (fixed frames, review pills) are dropped at port; `App.css`/`tokens.css` win over prototype styles.
10. **Data may outrun the engine.** Authoring is never blocked by what the runtime can evaluate; the editor warns loudly (the engine-lag layer), never blocks.

## 2. Anti-goals & phase boundaries — consolidated

**Phase boundaries (sequencing, not product scope):**

- **Physics/feel tuning is out of scope for every Phase 0 and Phase 1 row** — "do not drift into physics" binds those builds. It is *not* a product anti-goal: it is Phase 2's spatial stage, built after Phases 0–1 ship. Phase 0's only physics obligations are two format reservations: the registry bands slot (row P0-1) and `world update`'s reusable protected-wall core (row P0-6).
- **Dungeon playtest in cradle** — levels and combat across classes, skills, enemies — is a Phase 2 outcome (W2.0 pull-in + session runtime), *deliberately* not a Phase 0 build (Q3): waiting prevents building a weak launcher in Phase 0 only to replace it in Phase 2. Phase 0's success criterion 2 is annotated accordingly (§3, row P0-13).
- **Dialogue:** Phase 0 ships the full authoring system + docked tester; Phase 1's writer authors with it; Phase 2 adds only the live in-game scene half. **Sandboxes:** Phase 2 only. Phase 1's "not the dialogue tester, not the sandboxes" is an ownership line, not a deferral.
- **No 3D game template in Phases 0–2** — but nothing in any phase bakes a 2D, resolution, or engine assumption into registry schema or wizard data (W2.4's rule).

**Product anti-goals (all phases, deduplicated):**

- No migration of existing worlds; read-both compat shim, never a migrate verb. MazeWorld legacy packs stay untouched (incl. by `bible synthesize`).
- No on-disk schema rename in v1 (`maze_*` names stay while `pack_type` says dungeon); type renames v1.1; `db evolve` does field renames only.
- No template-upgrade contract; a diverged project is its own lineage. `pack promote` is named and deferred.
- No world-map surface for dungeons in v1; no "Floors" vocabulary until the manifest has real grouping — the UI never promises structure the data doesn't have.
- No third wizard card and no variant/preset axis; lava_world-style games are project evolution, not templates.
- The agent is not a new write path, not a pipeline replacement (run/resume/regen DAG verbs fenced), and never edits canon's source, cradle's source, or shared templates — code tools touch only the project's own engine copies; shared-template and canon-core changes route through the dev.
- Local, single-user app; the service dies with cradle. Hosting, accounts, multi-user/web are out of scope — the I1–I8 invariants (doctrine 8) are the only forward obligation these phases carry.
- **The sandbox never generates.** Editors make; the sandbox tunes and plays. Generation has many doors, four destinations; a door never runs a paid job silently.
- **No in-app mesh surgery — the three-tier commitment.** Weight painting, sculpting, manual UV seams are not built; each exists only as a disabled control with its reason. Reversing this is an architecture change. "The agent does operations, not art" is load-bearing copy.
- No video generation anywhere in cradle.
- The asset library is designed, not built; backend untouched; build gated on the user's reuse conversation (W2.3).
- Merge/save is always a human act; no agent-initiated unconfirmed spend; no auto-restart after crash; no NPC mood state machines; no camera-zone runtime in v1 (present-disabled).
- Torch extras stay out of the bundle; auto-updater deferred; distribution stays GitHub Releases (macOS signed+notarized, Windows unsigned).

**F. Skills and recipes — one loader, two kinds, template-integrity precedence (C13; ASSUMPTION-13 ratified at merge, Q5).** P1-A4.5's loader handles two kinds from day one: instruction-markdown skills (allowlist ⊆ host specialist's, optional model preference, trigger line) and canon-authored parameterized **recipes** (fail-closed parameter bounds + per-recipe gate configs — mesh_smith's bpy recipes are the first family). Precedence, ratified: **project-local wins within the project** — a project may add skills, add recipes, and override or widen *its own copies* of template recipes exactly the way it evolves schemas (journaled, project-scoped, deliberate — the band-widening idiom). **Template integrity:** a project's expansions never flow back; a new project from the same template gets the standard template. Safety invariants that survive any override: a skill never widens tool permissions (allowlists intersect, tiers still apply); the agent never authors free bpy (ASSUMPTION-4 intact — an overridden recipe is still a bounded recipe); bound-widening is a journaled user-level act, never a silent skill effect. Three hard edges make that last invariant real: recipe bound/gate-config **widening is never Always-allow-eligible** — it confirms per instance, like paid (tightening via override rides the ordinary ask tier); **no tool in Phases 0–2 writes skill or recipe files** — authoring them is a user act; and the schemas/band idiom's standing grants never extend to the recipe family.

**G. The condition grammar (C20).** One vocabulary, pack-registry data, one evaluator (Phase 0 §7.1: `has_item · quest · time · player · flag · segment · room · scene · event` + scene-only `actor:`). Phase 2's music-section conditions are a **scope-legal subset of this vocabulary**, evaluated by the same engine-evaluable-namespaces mechanism — never a second audio-only enum.

This amends §5.1b's list by those two fields.

**I. The engine-copy model (C1).** Phase 1 §7.1 is carried in its R1-amended form only: a pack carries one engine copy per attached engine (Godot; pygame after W2.0's promotion), each stamped in `.engine.json` and `game_coder`-evolvable; `edit_project_code` reaches any engine copy, never shared templates.
